# 决策：网络架构演进（netlink 熔断 → 容器内置内核 + TUN）

> 最重要的一次**架构纠正**。前三轮 spike 方向错了，被用户一句话拉回来：
> 「我们把 clash 这种功能集成到容器里不就可以了吗，外部只是一个辅助修改。」

## 演进路径

| 阶段 | 架构 | 问题 |
| --- | --- | --- |
| ≤1.0.21 | `HTTP_PROXY` 应用层代理 | 不读环境变量的程序、DNS、raw socket 全绕过 |
| 1.0.22~1.0.36 | netlink 删默认路由（fail-closed） | 只保证送到宿主代理端口，管不到代理软件拿到后怎么发 |
| 1.0.37 | 容器内 mihomo + TUN 全量接管 | 宿主软件彻底退出运行时链路，默认并存可选 |

## 旧链路的盲点

net-guard 删默认路由保证「流量一定送到宿主 7897 端口」，但：

- 看门狗只探 `generate_204` HTTP 码，国内直连也返回 204 → 运行中把 Clash 切 Direct 后
  界面继续显示旧境外出口（静默假绿）。
- 宿主 Clash 的 fake-ip（198.18.x）会污染 VM 的 DNS。
- 「要不要关 Clash」「怎么排污染」困扰了三轮 spike。

详见[直连盲点](../network/03-直连盲点.md)。

## 架构纠正

**容器内自带内核 + 配置 + TUN，宿主 Clash 只是导入/编辑 YAML 的辅助工具，运行时链路里没有它。**

```
应用（无 -x / 无 HTTP_PROXY / Chrome 无 --proxy-server）
  -> TUN Meta（table 2022 策略路由覆盖）
  -> 容器内 mihomo（DNS 127.0.0.1:53、fake-ip 198.19.x）
  -> 用户 YAML 里的上游节点 -> eth0 on-link
net-guard 仍删 main 表默认路由，作为 fail-closed 底座
```

按此重做，「宿主切 Direct 假绿」「DNS 被宿主 fake-ip 污染」「要不要关 Clash」三个问题
一次性消失，**用户不需要改任何宿主设置**。

**我错在哪**：把测试脚手架（spike 里拿宿主 7897 当上游）当成了产品架构。
这是本轮最大的教训 —— 先问「产品的形态应该是什么」，再设计验证，别让验证环境反过来定义产品。

## 兼容策略

用户拍板「TUN 并存可选，默认仍走旧链路」：加开关，导入 YAML 并开启后才切 TUN。
风险最低、可随时回退，代价是两套网关代码一起维护一阵。

## 实测验证（四轮 spike）

1~3 轮：确认 TUN 接管其实生效（netlink 全表 dump 看到 table 2022，
`/proc/net/route` 只看 main 表是误判）；定位宿主 Clash DNS 污染；
踩到 MMDB 初始化死锁。
第 4 轮按正确架构重做，**全绿**：DNS 归属 198.19.0.4（容器内分配）、
裸 curl 三源出口一致、`state=guarded`、杀内核立刻全断、清理复原。

完整报告 `build/TUN-SPIKE-结果.md`。产品链路验证 `build/tun-product-verify.sh`。
