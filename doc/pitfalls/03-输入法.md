## 9) 中文输入法必须走 IBus，不能走 fcitx5；且 daemon 要挂在常驻会话里。

> 注：这是 1.0.26 时期的历史结论。1.0.34 起已改走 fcitx5（见坑 18），本条保留作为演进依据。

WSLg 只转发按键、**不转发 Windows IME 的 preedit 组合串**，所以把输入法放进 VM 内部就能绕开：
按键 → X server → xterm(XIM) → IBus → Rime → 中文提交进 pty。

- **fcitx5 5.0 起移除了 XIM**（只剩 DBus/GTK/Wayland）。实测 `fcitx4frontend` 补了 dbus 后
  确实加载，但 `xprop -root XIM_SERVERS` 始终 `no such atom`；xterm 只认 XIM，这条路是死的。
- 换 `ibus-daemon -d --xim` 立刻得到 `XIM_SERVERS(ATOM) = @server=ibus`，`ibus engine rime` 也能切。
  Ubuntu 22.04 里 XIM 支持在 `ibus` 主包（`/usr/libexec/ibus-x11`），**没有 `ibus-x11` 这个包**。
- `fcitx4frontend` 的 `[Addon/Dependencies] 0=dbus` 意味着 WSL 没有 session dbus 时它连加载都不做；
  光补 `dbus-launch` 也不够（XIM 仍不注册），别在这条路上继续耗。
- **词库选万象 Pure**：`amzxyz/rime_wanxiang` v18.1.8 的 `rime-wanxiang-pure.zip`（26.6MB）。
  Base/Pro/Lite 依赖 Lua 插件，我们只有 librime 1.7.3；Pure 官方定位「老系统/无 Lua」，
  实测成功编译出 `wanxiang_pure.table.bin`（59MB）。包内自带 `opencc/`，仍可打繁体。
  zip 放在 `vm/assets/rime/`，由 `sync-scripts.js` 同步到 `runtime/assets/rime/` →
  打包进 `resources/assets/rime/` → `syncScripts` 复制到 `/opt/assets/rime/` →
  `rime-setup.sh` 离线解压。**不依赖首次启用时 GitHub 可达**。
- `pack-dev-src.py` 的 `SKIP_EXT` 默认排除 `.zip`，必须为
  `claude-vm/vm/assets/rime/` 开例外，否则换机开发时源码包里没有词库。
- 词库是 **CC BY 4.0**，包内自带 README/许可，重新分发要保留署名。
- 全部包用 `--no-install-recommends`：**零字体依赖**，不碰 checkcc 的 17 个硬编码字体家族名。
  中文渲染继续用 `Noto Sans SC`。
- `ibus-rime` 的用户目录是 `~/.config/ibus/rime`（不是 fcitx5 那个），`default.custom.yaml` 里
  `patch: schema_list: [wanxiang_pure]`（1.0.24 起由万象词库替换掉 `bopomofo_tw`）。
- **跨会话环境变量**：用户点「打开终端」是新起 `wsl.exe`，继承不到 entrypoint 的 export。
  必须把 `XMODIFIERS` 写进 `/opt/config/runtime-env`，再让 `run-*.sh` source 它，
  并给 xterm 加 `-xrm "XTerm*inputMethod: XIM"`。
- **daemon 生命周期**：`ibus-daemon -d` 挂在一个一次性测试脚本下，脚本退出后进程就没了，
  于是下一次 `ibus engine` 报 `IBUS_IS_BUS assertion failed`。产品里它由 entrypoint 常驻会话拉起，
  和 `sleep infinity & wait` 是同一条生命线。
- `zh_TW.UTF-8` 镜像里没预生成，entrypoint 1.5 段现场 `sed /etc/locale.gen + locale-gen`，
  一次生成后持久保留，不用重建 rootfs。
- **仍未自动验证的一步**：真实 WSLg 窗口里按 `Ctrl+Space` 打字是否进 Claude Code。
  1.0.26 已把自动化推到「XIM server 注册 + 引擎切换 + 词库编译 + xterm 建立 IM 上下文 +
  按键送达 pty」，但 xdotool(XTEST) 注入的按键不触发 XIM 组合（落盘仍是 `nihao `），
  详见坑 11。不要拿这个自动化结果当成「Rime 可用」的证据，仍需真人按一次。

## 11) 1.0.25：繁体字体、独立身份、xterm 的 openIm。

- `Noto Sans TC` 与名单里被点名的 `Noto Sans CJK TC` / `PingFang TC` / `Source Han Sans TC`
  是**不同家族名**（`fc-scan` 实测），装它不扣分；SC 显示繁体笔形偏简才需要它。
  两份字体共 29MB，走 `vm/assets/fonts → runtime/assets/fonts → /opt/assets/fonts →
  /usr/share/fonts/truetype/claude-{sc,tc}` 这条链，别只放一边。
- **独立身份只生成一次**：WSL 继承宿主计算机名（`HomeVisionPC`），`/var/lib/dbus/machine-id`
  来自 Docker 模板、所有安装相同。entrypoint 2.67 生成 `DESKTOP-XXXXXXX` + 新 machine-id
  并写进 `/opt/config/identity`，之后复用。**每次启动都换反而更像新机器**，别做。
- **xterm 372 默认不开 IM**：只给 `-xrm "XTerm*inputMethod: XIM"` 不够，按键会全被当
  ASCII 送进 pty；必须再加 `XTerm*openIm: true`（加了才会出现与 IBus 协商 preedit 的日志）。
  `preeditType` 用 `Root`，`OverTheSpot` 会被 IBus 拒绝。两个 `run-*.sh` 都要一致。
- **自动化边界**：xdotool 用 XTEST 注入按键，能进 pty 但**不会触发 XIM 组合**；
  别据此判断 Rime 可用/不可用，最后一步必须真人在 WSLg 窗口按。
- **apt 不读 `HTTP_PROXY`**：熔断锁定后装包报 `Network is unreachable`（USTC 镜像直连不通）。
  测试里要 `apt-get -o Acquire::http::Proxy="http://宿主:端口" install ...`；
  产品里 Rime 首次启用走 entrypoint 已导出的代理变量，不受影响。
- 首次启动验证做法：把状态恢复成刚导入（删 identity、Chrome 语言重置成 en-US、
  resolv.conf 加回 search 域、删 TC 字体目录），再用
  `awk '/^# 2\.65\)/,/^# 3\)/'` 抽出 entrypoint 的真实段落执行 —— 比手写复现可靠。

## 16) 1.0.31：终端里一个中文都打不进，Chrome 候选窗飘在左下角 / 字形变方块。

- 用户截图：Chrome 输入框里 preedit `wo o s`，候选窗却贴在屏幕最左下角、竖排 1–9
  且中文字形是豆腐块；Claude Code 终端则完全无法输入中文。
- **不是配置没生效**：`ready=desktop`、ibus-daemon / ibus-x11 / ibus-engine-rime 全在、
  `XIM_SERVERS=@server=ibus` 注册成功；`zh_TW.utf8` 已生成、`fc-match` 正常返回
  Noto Sans SC/TC —— locale 与字体都排除。
- **真因**：镜像里**没装 `ibus-gtk3`**（缺 `im-ibus.so`），但 `runtime-env` 写了
  `GTK_IM_MODULE=ibus` → GTK 应用（Chrome / 终端）整体降级到 XIM；
  xterm 是纯 Xt、本来就只认 XIM。IBus 的 XIM 前端只支持 `preeditType: Root`，
  候选窗是独立 X 窗口、拿不到光标坐标，输入上下文在 xterm 上常常根本建不起来。
- **选型先量体积**：`ibus-gtk3` 80KB、`lxterminal` 593KB（GTK3+VTE）、
  `sakura` 272KB、`xfce4-terminal` 2448KB 且要拉 8 个 xfce 库。
  选 lxterminal：最小、项目里已有同色值的 `vm/config/lxterminal.conf`。
  **没换 fcitx5**：那要迁词库到 `~/.local/share/fcitx5/rime`、显式起 D-Bus 会话、
  改写守护脚本探活与自检，复杂度远大于候选框皮肤那点收益。
- **改动**：`rime-setup.sh` 按需装 `ibus-gtk3 lxterminal`（`need` 检查加两项）；
  `run-terminal.sh` / `run-claude.sh` 换 lxterminal 并**删掉全部 `-xrm` XIM 资源**；
  `entrypoint.sh` 把 `/opt/config/lxterminal.conf` 部署到 `~/.config/lxterminal/`；
  `check-env.sh` 自检先查 `im-ibus.so` 再查 XIM atom。
  `ibus-daemon -d --xim` 保留作老 Xt 兼容，D-Bus、词库、desktop-guard 探活全部不动。
- **验证**：隔离 `:9` 冒烟 —— X 可用、XIM atom 注册、GTK3 `immodules.cache` 命中 ibus、
  lxterminal 稳定存活且无 IM 模块加载报错。组合输入仍需真人按 `Ctrl+Space` 敲 `nihao` 确认。
- 教训：**协议层死结别靠加参数硬凑**（1.0.26 的 `openIm` / `preeditType` 就是），
  先确认应用实际走哪条输入链路；`GTK_IM_MODULE` 设了 ≠ 模块装了。改运行时脚本记得
  `RUNTIME_REV` +1（5→6）。

## 17) 1.0.33：中文输入「看起来坏了很久」，真因是 XDG_RUNTIME_DIR 属主错配 + 脚本没进环境（坑 13 变体）。

- 用户 11 月 9 日实测：串流模式下终端一个中文都打不进，Chrome 候选窗飘左下角 / 字形豆腐块；
  1.0.31 的 lxterminal+ibus-gtk3 修复「明明装了」却毫无效果。
- **第一层（坑 13 再现）**：VM 里 `/opt/scripts/run-terminal.sh` 还是 11-06 的老 xterm+XIM 版，
  1.0.31 新脚本从未进入正在跑的环境 —— 所有手工验证都测的是老链路。
- **第二层（真根因）**：WSLg 把默认 `XDG_RUNTIME_DIR` 建在 `/mnt/wslg/runtime-dir`、属主 uid 1000，
  而会话以 root 跑。GLib/GTK3 在属主不匹配的运行时目录上**卡死在初始化**：
  lxterminal 进程活着、窗口永远不出现、零报错（曾在脏会话上误判成 im-ibus 卡死、
  D-Bus autolaunch 竞态等，都错了）。换成 root 自己的 `XDG_RUNTIME_DIR=/tmp/claude-vm-runtime`
  （chmod 700）后第一次打字就出「你好」——输入法链路（im-ibus + Rime）其实一直是好的。
- **修复**：entrypoint 开头 export XDG_RUNTIME_DIR=/tmp/claude-vm-runtime + mkdir/chmod 700，
  并写进 runtime-env（499 行）让所有 GUI 子进程继承。
- **排查方法论教训**：
  a) 短命 wsl.exe 脚本用 setsid 拉 entrypoint 会随客户端退出被 WSL 回收整棵进程树
  （setsid 挡不住）——测会话必须用常驻 wsl.exe 后台任务当宿主（产品 spawn 同款形态）；
  b) Rime 的 Shift 中英模式**跨实验粘滞**，xdotool 合成按键也会过 IME 预编辑——
  合成打字测试必须自适应重试（命令没落盘就 Escape+Shift 重试）并跟踪模式，否则会把
  「命令被吞进预编辑」误判成「按键没落盘」。
- **最终实测（产品路径：真实 entrypoint + run-terminal.sh + lxterminal + im-ibus + Rime）**：
  nihao→「你好」✓；Shift 切英文 nihao→英文字面 ✓；Ctrl+Space 挂起 abc→纯 ASCII ✓。
  三个切换快捷键全部通过：Shift=Rime 中英切换，Ctrl+Space=引擎挂起/恢复，Ctrl+Shift=切引擎。
- 1.0.33 同时修复 1.0.32 引入的启动回归（backend 模块 vs 实例接线错误，TypeError 炸掉
  runtime:status）。RUNTIME_REV=6→7。

## 18) 1.0.34：IBus 候选面板在 VNC 里到天花板，换 fcitx5 + 三个隐蔽陷阱。

- 用户截图定性：候选窗钉在屏幕左下角不跟光标、竖排 1-9 老样式、前两项豆腐块 ——
  IBus 面板自身的问题（定位协议 + 字体回退），1.0.26~1.0.33 七轮修补后再无进展。
  Rime 引擎与万象词库一直没问题，坏的是「壳」。
- **换 fcitx5**（国内 Linux 桌面事实标准）：面板跟手、横排候选、字体正常。
  fcitx5 5.0.14 + fcitx5-rime 5.0.11 镜像里已有，只补装 fcitx5-frontend-gtk3（2 包约 1MB）。
  词库迁到 fcitx5-rime 的用户目录 ~/.local/share/fcitx5/rime（rime-setup 一次性
  从 ~/.config/ibus/rime 迁移，排除 build/ 跨引擎重编，避免 146MB 重新解压）。
  fcitx5 没有 XIM 前端 —— 主链路本来就是 GTK3 im module（lxterminal/Chrome），
  不需要 XIM。fcitx5 profile 写 DefaultIM=rime（无图形界面配置法）。
- **陷阱 1（guard 误杀）**：desktop-guard 在 entrypoint 的 D-Bus 导出**之前**启动，
  它的 fcitx5-remote 探活永远失败 → 4 秒一轮杀掉重拉 fcitx5（日志反复
  Unloading/Loading addon、打字时好时坏）。修：D-Bus 会话总线创建提前到 guard
  之前（dbus-launch，dbus-daemon 固定 socket 兜底）。
- **陷阱 2（激活语义）**：fcitx5 进程活着 ≠ 可输入。默认 state=1（关闭，按键透传
  成 ASCII）；实测 `-s rime` 切引擎那步才真正激活到 state=2，`-o` 单独只到 1。
  修：entrypoint/guard 重启后都发 `-s rime` + `-o`（顺序：先 -s 后 -o，留重试）。
- **陷阱 3（测试互踩）**：Ctrl+Space 是 1↔2 状态开关，跨实验粘滞 —— 上一轮留 state=2，
  下一轮按 Ctrl+Space 反而关掉，表现为「行为时好时坏」。合成打字测试必须先
  `fcitx5-remote` 读 state 再决定是否按开关，且 xdotool 合成键会进 Rime 预编辑
  （state=2 时连 `cat >>` 命令都被吞）。
- **实测全过**：nihao→你好 ✓；Shift 切英文 nihao→英文字面 ✓（Rime 内中英）；
  Ctrl+Space state 1↔2 开关 ✓。快捷键表：Ctrl+Space=输入法开关，Shift=中英切换。
- 教训：**「壳」的问题不要用「引擎」的复杂度去修**（fcitx5 只换壳、词库全复用）；
  后台守护的探活依赖必须先于守护启动就位；服务「起来」和「可用」之间隔着激活语义。

## 19) 1.0.35：候选窗横排跟手了，但生僻字仍是方框（缺 CJK 扩展 B 区字形）。

- 用户截图（1.0.34 实测）：候选窗已跟手横排，但 2/3/5/6/8 号候选是方框。
  把「wo」的候选真实上屏抓出来：`我 𤻌 𦯏 握 𦰖 𦷵`
  —— 我/握在基本区正常，其余 4 个是 U+24ECC / U+26BCF / U+26C16 / U+26DF5，
  全在 **CJK 扩展 B 区（U+20000+）**。万象词库把地名/古字排进了高频候选。
- 镜像只有自带 Noto Sans SC/TC（子集字体）：`fc-list :charset=20000` **空**，
  `fc-match sans` 是 DejaVu Sans，中文靠回退；扩展区无字形 → Pango 画 tofu。
- **修法**：按需装 `fonts-hanazono`（22MB / 落盘 52MB，HanaMinA/B，
  家族名「花園明朝」不在 checkcc 的 22 个名单家族里）。装后 U+20000/2A700
  区间有覆盖，4 个生僻字全部 `→ HanaMinB`；而 `fc-match sans` 仍是 DejaVu、
  `sans:lang=zh-tw` 仍是 Noto Sans SC —— **默认渲染与检测评分都不变**。
  字体回退是按需的：Noto 已有的字仍走 Noto，只有缺字形的才落到 HanaMin。
- **不能用 `fonts-noto-cjk-extra`**：214MB 且家族名 "Noto Sans CJK SC/TC"
  直接命中指纹名单扣分。need 检查用 `fc-list ':charset=20000' family`
  按「码位有没有字体覆盖」判定，与具体包/文件解耦；装完 `fc-cache -f`。
- rime-setup 的自检字体名单保持完整（不靠删名单蒙混），静态断言加 2 例。
- 遗留（非 bug）：即使有字形，万象大字集仍会把生僻字排进前 9 候选，
  打「wo」看到 𤻌/𦯏 属词库特性；若嫌吵要另外在词库层做字符过滤
  （会改动 146MB 词库并重编译，本次不做）。

## 20) 1.0.36：输入 `ffff` 时候选窗整个消失、退格全盲（零候选 + client preedit 叠加）。

- 用户报告串流 / wslg 两模式都复现。在 Xtigervnc :1 + openbox 隔离复现：
  GTK IM 探针证明**预编辑链路完全正常**（`f→ff→fff→ffff`，退格依次 `fff→ff→f`），
  Rime / fcitx5 / GTK im module 都没坏，别再去修引擎或词库。
- 真因：`ffff` 在万象全拼里不是合法编码 → 零候选 → **classicui 把候选窗 unmap**
  （实测 `0x40000d` 由 IsViewable 变 IsUnMapped，删到合法声母 `f` 才恢复）。
  叠加 fcitx5 默认的 **client preedit**（编码交给应用画、候选窗里不显示输入码）：
  窗口一 hide，应用（尤其 lxterminal/VTE 里的 Claude Code 终端）又没画 preedit，
  于是既无候选也无编码，按退格完全盲。这是 classicui 的窗口映射逻辑，
  **与 X server 是 WSLg 还是 Xtigervnc 无关**，所以两个模式表现一模一样。
- **修法**：`rime-setup.sh` 写 `/root/.config/fcitx5/config`：
  `[Behavior]` / `PreeditEnabledByDefault=False`（配置项从 `libFcitx5Core.so.7`
  的 strings 挖到，描述是 "Show preedit in application"）。关掉 client preedit 后
  由 classicui 自己画编码，零候选时窗口保持 IsViewable 并显示输入码；
  落地后实测 `ffff` 与退格 1 次的 Map State 全部 IsViewable。
- 顺带修 `page_size`：之前写成 9，但万象 `default.yaml:16` 明写「候选词个数
  不得超过 6 个，7890 代表声调」，按 7/8/9 是声调筛选、不是选字；改回 6，
  截图确认候选栏回到 1-6。
- 复现与验证工具：`build/ime-repro.sh`（Xtigervnc :1 隔离会话）、
  `ime-probe-gtk.py`（Gtk.IMMulticontext 记录 preedit/commit）、
  `ime-shot.py`（GdkPixbuf 抓 root 窗口）、`ime-trial.sh`（配置项试验，自动还原配置），
  截图在 `build/shots/`。静态断言 +2 例，`RUNTIME_REV` 9→10。
- 两个陷阱：探针把 `realize` 信号接在 `show_all()` 之后 → IMContext 从未绑定窗口、
  字母直接 commit，会误判成「Rime 没激活」；`fcitx5-remote -o/-s` 必须在
  **有焦点窗口之后**执行，否则作用于空 InputContext、state 一直是 0。
- 同步范围：真源 `claude-vm/vm/scripts/rime-setup.sh` → `sync-scripts.js` 生成
  `runtime/scripts/` 副本 → 已安装应用的 `resources/scripts/` → VM 的 `/opt/scripts/`，
  并在 VM 内直接执行一次脚本写配置。少任何一层都会回到「修复在包里、不在环境里」。
