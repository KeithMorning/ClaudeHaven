## 3) Chrome 的 `--proxy-server` 不接受尾斜杠。

`http://host:7897/` → `ERR_NO_SUPPORTED_PROXIES`，`http://host:7897` 才正常。
`local-proxy` 文件里的值、entrypoint、check-env、main.js 四处都做了去斜杠，改动时别漏。

## 8) 代理必须是唯一出口，且熔断要发生在业务启动之前。

这个精简 rootfs **没有 iptables / nft / iproute2**（连 `ip`、`route` 都没有），但
`CapEff=000001ffffffffff` 含 `CAP_NET_ADMIN`，Python3 有 `AF_NETLINK` ——
所以 `net-guard.py` 直接发 `RTM_DELROUTE` / `RTM_NEWROUTE` 改内核路由表，
**不要为了这个去重打 720 MB 的 rootfs 装 iptables**。

几个不能改的点：
- WSL 路由是 `default via <网关>` + `<网关网段>/20 dev eth0 scope link`。删掉 default 后
  on-link 那条还在，宿主代理仍可达；其余目标 `ENETUNREACH`。代理是公网 IP 时才补 `/32`。
- **IPv6 必须一起关**（sysctl + 删 v6 默认路由）：只封 v4 是最常见的泄漏口。
- **顺序**：先 `lock`（毫秒级）→ 再预检 → 再验证"直连确实出不去"。反过来会在预检那几秒
  留下业务流量直连的窗口。
- 预检不过**不解锁**，保持封锁并写明 reason；`net:status` / 自检都读状态文件。
- 守卫退出时**不要 unlock**（fail-closed 语义）；恢复只在显式 `NET_GUARD=off` 或重启发行版。
- 看门狗间隔 3 秒只为兜住「WSL 网络重置把默认路由加回来」；正常的代理断开不依赖它。
- 坑：`cmd_lock` 里 `cmd_status()` 的返回值已带 `onlink` 键，不能再 `dict(ok=..., onlink=...)`
  传一次，否则抛 `multiple values` —— 路由其实改完了却对外报失败（1.0.22 开发时踩过）。
- 坑：测试时用**多行** `bash -c '...'` 经 `wsl.exe` 传参，换行会被吞、变量赋值失效，
  还照样打印成功标记。产品里的 `syncScripts()` 是单行 `; ` 拼接，不受影响；
  临时验证请用脚本文件或单行命令。

## 15) 1.0.30：「停止→启动」必现「代理在本机可以连上，但容器内连不到它」。

- 报错文案是**误导**的，和 Allow LAN 没关系。`vm.log` 里每次都是
  `[start] 版本 ...` 后约 1 秒 `[start] 上游代理解析失败：...`，**没有 `spawn:` 行** ——
  卡在 `resolveUpstream`，发行版根本没被拉起。
- 决定性证据：`cat /proc/net/route` 只剩 `eth0 00F0A8C0 00000000 ...`（192.168.240.0/20
  直连），`00000000` 默认路由不见了；`/run/claude-vm/net-guard.orig` 也不存在（tmpfs）。
- **根因链**：`net-guard.py lock` 用 netlink 删默认路由实现 fail-closed →
  `wsl --terminate` 只停发行版、**不重建 WSL2 网络命名空间**，删除的路由残留 →
  `wslGateway()` 靠默认路由算宿主地址，返回 null → `resolveUpstream` 失败 → 不 spawn →
  死锁。**实测只有 `wsl --shutdown` 才恢复默认路由**（`net-guard status` 从
  `locked:true / default_v4:null` 变成 `locked:false / default_v4:192.168.240.1`），
  所以 `net-guard.py` 注释里「重启虚拟环境会自动恢复」是错的，已改掉。
- **修法 1（根治）**：`wslHostCandidates()` 一次 WSL 调用取三来源 —— 默认路由网关、
  直连网段 `.1`（解析 `/proc/net/route` 的小端 hex + mask）、
  `/opt/config/local-proxy` 上次成功的宿主地址；`resolveUpstream` 把全部候选交给
  `wslProbeHosts` 做真实 TCP 探测，只采用可达的非回环地址。端到端实测：正常态与
  「剥掉默认路由行」的故障态都返回 `http://192.168.240.1:7897`。
- **修法 2（收尾）**：`stopRuntime()` 在 `runtimeProc.kill()` **之前**跑
  `python3 /opt/scripts/net-guard.py unlock`。顺序不能反：kill 后 `/run` 会话消失，
  ORIG_FILE 就没了。主动停止属受控收尾，解锁安全；意外退出仍保持 fail-closed。
  实测 lock→unlock 往返 `ok:true`，默认路由与 IPv6 都还原。
- 诊断文案改为区分「容器内没有默认路由（熔断锁定，属预期）」与「Allow LAN 未开」，
  别再把用户往代理软件设置上引。改了运行时脚本记得 `RUNTIME_REV` +1（4→5）。

## 22) 容器内内核接管时，宿主代理不是运行时依赖。

把 Clash/mihomo 放进镜像、用 TUN 在网络层接管，宿主软件只负责编辑 YAML。
四条硬约束见[内置 Mihomo + TUN](../network/02-TUN与Mihomo.md)：内核必须先于熔断启动且 MMDB 预置、
DNS 收进 127.0.0.1 并等 `tun-ready`、TUN 分支一律裸 curl、YAML 用 base64 分块注入。
**别再回到「要不要关宿主 Clash」这条路上去** —— 那是把测试脚手架当成了产品架构。
